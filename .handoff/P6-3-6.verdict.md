## P6-6 (F9 probe): ACCEPT
- `SELECT count(), uniq(..) FROM (SELECT .. LIMIT {lim:UInt64})` with `max_threads=1` (int) works on a real engine
  with a subquery; on a 4-part, 200,000-row table the count is exactly the cap for caps 1, 1000, 123456, 200000
  and 250000 (min(cap, rows)). `max_rows_to_read` and `read_overflow_mode` are gone.
- Failing probe stays a STATS_UNAVAILABLE diagnostic with no error text; a table whose name is not plain is
  swallowed the same way (the `_quoted` call is inside the try).
- Observation (pre-existing, not a defect of this change): `uniq` is a sketch. 100,000 distinct ids read as 100,315;
  `_probe_profile` clamps to 1.0, so a column with about 1 percent duplicates can read as fully unique. `uniqExact` is the upgrade.

## P6-3 (F7 tokens): ACCEPT with findings the lead should decide on (none is a regression of a derived check)
Holds: one bounded read per table, plain non-nested columns, key and key id as PostgreSQL, `complete` boundary
(30 rows: limit 31 true, limit 30 false, limit 7 on 200,000 rows false with sample_count 7), budget charged before each
read and `BudgetExhausted` raised exactly like PostgreSQL (through `collect`: OperatorError "configured limit", no bundle,
no traceback), a table `Page Views` or a column `my col` skips instead of aborting (tokens and probe on), View and
LiveView not read, no log/print call in the new code, statements carry identifiers and a bound int only.

Findings (each pinned by a test; severity is my view, the decision is the lead's):
1. Types the real driver returns. Tokens publish for String, UInt/Int (incl. Int256), Decimal (12.50 -> "12.5", same
   text the PostgreSQL numeric gives), Float64, Enum8 (str), LowCardinality(String), LowCardinality(Nullable(String)).
   NO entry, no crash, for UUID (uuid.UUID), Date/DateTime/DateTime64 (date/datetime), IPv4/IPv6 (ipaddress objects),
   FixedString (bytes) and Bool. Nullable None is dropped correctly. Cross-engine consequence: an absence, never a
   wrong match; a ClickHouse UUID key against a PostgreSQL uuid (pg8000 also returns uuid.UUID) or a Mongo string uuid
   stays "value overlap not measured", and a ClickHouse String holding uuid text tokenises against nothing on the
   other side. `str(uuid.UUID)` equals PostgreSQL `::text` and a Mongo string uuid, so adding UUID to the shared
   `_token_text` is a one-line change that helps all three engines; dates and bytes have no agreed text, leave them.
   Test: `test_finding_uuid_date_datetime_ip_fixedstring_bool_publish_no_tokens`. Minor: Float32 1.1 arrives as
   1.100000023841858 (token never equals "1.1"); Decimal wider than 28 digits is rounded by `normalize()` (shared path).
2. Any server error on the value read aborts the whole collection (the probe catches the same error). Real case on a
   real engine: a table with an EPHEMERAL column (listed by system.columns, `SELECT` raises NO_SUCH_COLUMN_IN_TABLE),
   and a File/Kafka/S3/URL/remote-engine table whose source is gone or whose grant is revoked. Both reproduced
   (`test_a_table_with_an_ephemeral_column...`, `test_one_unreadable_table...`, strict xfail). Recommendation: read
   `default_kind` in the columns query and skip EPHEMERAL; wrap the per-table read like the probe and emit a code-only
   diagnostic (needs a new or reused diagnostic code, contract change, so a lead decision).
3. Related leak path: the server's error text from a value read goes out as an uncaught traceback (the collector
   only converts OperatorError). ClickHouse parse errors on File/URL/S3 tables quote the offending input, so a value
   can reach the terminal (`test_a_server_error_text_from_a_value_read_does_not_reach_the_console`, strict xfail,
   fake client). Fixing 2 with a code-only diagnostic fixes this.
4. Materialized views. Skipping is wrong for a MaterializedView WITHOUT `TO`: its rows are stored in a hidden
   `.inner_id.<uuid>` table that system.tables lists but whose name fails `_PLAIN_COLUMN`, so neither is ever read,
   and the PostgreSQL path reads matviews (`kind in "rmp"`). Verified on a real engine that
   `SELECT .. FROM mv LIMIT n` returns the stored rows (does not run the view query). Recommendation: read
   `MaterializedView`, keep skipping `View` and `LiveView` (they run their query). An MV with `TO` duplicates the target
   table (harmless, same tokens). Needs the one-line set change `{"View","LiveView"}`.
5. Low: a namespace such as `my-db` goes to `_quoted` unguarded and raises ValueError (traceback, no bundle) when
   tokens are on; with only the probe on it is a diagnostic, with neither it works. PostgreSQL has the same weakness
   for a schema. Recommendation: skip with the same rule as the table name.
6. Low: tokenising is charged first, so a budget that exactly fitted catalog + probe now gets tokens and silently loses
   the probe profiles (no diagnostic). Documented by `test_finding_tokens_are_charged_before_the_probe...`.
