## Assumptions the lead may overrule
- `path_max_hops` is `ge=1` (pinned). `path_max_bridge_tables` is only pinned to refuse negatives; whether 0 is allowed (disabling bridges) is not pinned.
- A "hop" is one relationship edge; `path_max_hops 3` is the three-edge fixture. The planner's `max_hops 4` has the same meaning.
- Shape: the bridge table is an item with `role: "path_only"` and `kind` other than `field`; its key columns are field items with `object_name` = bridge (any `role`). Key columns = columns named in the path's relationship lines (so the bridge's own key `lid` is excluded when no line uses it).
- Cap semantics when one path needs more bridges than the cap: not pinned (no half path required, at most cap tables). The unambiguous cap test uses two separate paths.
- `relationship_limit` interaction (limit 0, or a limit that cuts the path lines) is not specified, so not tested.
- Retrieval order of two items and `allowed` citation ids for path_only items: not pinned. Whether a path_only id is citable is the worker's choice; attack mode should read it.
